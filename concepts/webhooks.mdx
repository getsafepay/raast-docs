Raast workflows are asynchronous. Customers can approve or reject requests in their banking apps, and payment, payout, refund, and settlement states can change after the originating API request returns. Safepay sends those changes to your backend through webhooks.

## How webhooks work

<Steps>
  <Step title="Register an endpoint">
    Create an endpoint with `POST /v1/aggregators/{{aggregator_id}}/webhooks`. Subscribe to exact events or category filters such as `payment.*`.
  </Step>
  <Step title="Receive a signed event">
    Safepay sends an HTTP `POST` containing the event JSON and five `X-SFPY-*` delivery headers.
  </Step>
  <Step title="Verify and persist">
    Verify the timestamp and HMAC signature over the raw body, then persist the event idempotently using `X-SFPY-EVENT-ID`.
  </Step>
  <Step title="Acknowledge and process">
    Return a `2xx` promptly, then apply business logic asynchronously. Poll the corresponding API when reconciliation is necessary.
  </Step>
</Steps>

## Delivery headers

| Header | Purpose |
| --- | --- |
| `X-SFPY-EVENT-ID` | Unique event ID used for idempotency. |
| `X-SFPY-EVENT-TYPE` | Public event name used for routing. |
| `X-SFPY-AGGREGATOR-ID` | Aggregator that owns the event. |
| `X-SFPY-SIGNATURE` | HMAC-SHA256 signature. |
| `X-SFPY-TIMESTAMP` | UTC RFC 3339 delivery-attempt timestamp included in the signed message. |

The signature is calculated over `X-SFPY-TIMESTAMP + '.' + raw_body` using the decoded webhook secret. See [Webhooks delivery](/guides/webhooks-delivery) for the complete verification algorithm, retry rules, and rotation procedure.

## Event payloads

Every event uses a versioned envelope containing:

- event metadata such as `identifier`, `timestamp`, `kind`, `code`, and `version`;
- `aggregatorId` and, when applicable, `partnerId`;
- the public `webhookEventType`; and
- a resource snapshot under `subject.payment`.

See [Webhook events and payloads](/guides/webhook-events) for a field reference and complete JSON examples.

## Event families

| Family | Examples | Resource |
| --- | --- | --- |
| Payments | `payment.created`, `payment.completed`, `payment.settled`, `payment.failed` | Pay-ins, QR payments, and payouts. |
| Refunds | `refund.created`, `refund.completed`, `refund.failed`, `refund.canceled` | Individual refund lifecycle. |
| Settlements | `settlement.created`, `settlement.processing`, `settlement.completed` | Settlement lifecycle. |

Payouts are payment resources with `subject.payment.type` equal to `PAYOUT` or `SETTLEMENT_PAYOUT`; subscribe to `payment.*` for payout state changes. There is no `payout.*` event family.

## Reliability model

Webhook delivery is at least once and ordering is not guaranteed. Handle duplicate events and delayed earlier states safely. Safepay retries transport errors and `5xx` responses five times after the initial request. Any `2xx` acknowledges the delivery; terminal `4xx` responses are not retried.

<Callout type="tip">
  Store the event before acknowledging it, enforce a unique constraint on the event ID, and compare the current resource state before applying a transition.
</Callout>

## Secrets and rotation

The create and rotate responses return a base64-encoded signing secret. Treat every `secret` value returned by webhook-management APIs as sensitive. Decode it before computing HMAC-SHA256.

Rotation replaces the stored secret immediately; Safepay does not keep both secrets active. Because a request already in flight can still be signed with the old secret, retain the previous secret briefly as an aggregator-side verification fallback. See [Rotate the signing secret](/guides/webhooks-delivery#rotate-the-signing-secret).

## Manage endpoints and inspect deliveries

| Endpoint | Purpose |
| --- | --- |
| `POST /v1/aggregators/{{aggregator_id}}/webhooks` | Create an endpoint and obtain its signing secret. |
| `GET /v1/aggregators/{{aggregator_id}}/webhooks` | List webhook endpoints. |
| `GET /v1/aggregators/{{aggregator_id}}/webhooks/{{webhook_id}}` | Read an endpoint. |
| `PUT /v1/aggregators/{{aggregator_id}}/webhooks/{{webhook_id}}` | Update its URL, event filters, description, or enabled state. |
| `DELETE /v1/aggregators/{{aggregator_id}}/webhooks/{{webhook_id}}` | Delete an endpoint and its stored delivery records. |
| `PUT /v1/aggregators/{{aggregator_id}}/webhooks/{{webhook_id}}/rotate` | Replace the signing secret. |
| `GET /v1/aggregators/{{aggregator_id}}/webhooks/{{endpoint}}/deliveries` | List delivery summaries and filter them by status or event. |
| `GET /v1/aggregators/{{aggregator_id}}/webhooks/{{endpoint}}/deliveries/{{delivery}}` | Read a delivery, including its stored payload and last error. |

The delivery API surfaces `WD_PENDING`, `WD_DELIVERED`, `WD_FAILED`, and `WD_DEAD` (`WD_FAILED` is reserved and not currently assigned; deliveries stay `WD_PENDING` through retries). There is no public manual-redelivery endpoint; reconcile a dead delivery through the corresponding resource API.
